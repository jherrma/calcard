# Domain Layer

This is the innermost layer of the application. It contains the core business logic and state of the application, completely independent of any external frameworks, databases, or UI.

## Responsibility

The domain layer defines:

- **Entities**: Business models representing the core concepts.
- **Interfaces**: Crucial abstractions for data persistence and external services.
- **Domain Logic**: Business rules that are intrinsic to the data itself (e.g., password hashing methods on the `User` model).

## Subdirectories

### [user/](user/)

- `user.go` — Core user entity (profile data, security status, password hashing). `TokensValidAfter` (`json:"-"`, nil = never revoked) invalidates every access token issued before it; `AcceptsAccessTokenIssuedAt` is the single rule (a token issued at exactly the marker is accepted, so the replacement token change-password mints right after setting it survives). `DeletedIdentityPrefix` (`deleted:`) builds the tombstone a deleted account's e-mail and username are replaced with.
- `refresh_token.go` — Opaque tokens for session persistence, linked to users and client context (User Agent, IP).
- `email_verification.go` — Email verification token model.
- `app_password.go` — Application-specific passwords for DAV client access. The only scopes are `ScopeCalDAV` / `ScopeCardDAV` (`AppPasswordScopes()`, also the default for a create without scopes).
- `caldav_credential.go` — CalDAV-specific access credentials.
- `carddav_credential.go` — CardDAV-specific access credentials.
- `mcp_token.go` — Long-lived bearer credential for the `/mcp` endpoint (story 104). Unlike the DAV credentials it stores a **unique-indexed SHA-256** of a 256-bit random secret rather than a bcrypt hash: an MCP client presents only the opaque token, so it must be findable from that string alone, which a per-row salted hash cannot do. `TokenPrefix` is the only cleartext fragment, kept so a shown-once token stays recognizable in the settings list.
- `preference.go` — Per-user preferences (key registry, defaults, validation). `PrefTimezone` (`timezone`, #169) is pattern-validated: trimmed, then `LoadTimezone` (exported; non-empty, not `Local`, at most 64 bytes, `time.LoadLocation` succeeds), default `UTC`. "Not set" is the ABSENCE of a row, so an explicit `UTC` is distinguishable. `UserPreferenceRepository` also has `InsertIfAbsent` (`INSERT … ON CONFLICT DO NOTHING`) and `ReplaceValueIf` (compare-and-set on the old value). `LoadTimezone` duplicates `calendar.LoadEventLocation` on purpose: `domain/user` must not import `domain/calendar`.
- `validation.go` — User input validation logic, incl. `ValidatePassword` — the policy for a NEW account password: 8 to `MaxPasswordBytes` (72) **bytes**, an upper-case letter, a lower-case letter, a digit and a punctuation/symbol character, by Unicode class. The maximum is bcrypt's (x/crypto refuses longer input with `bcrypt.ErrPasswordTooLong` rather than truncating), so every site that hashes a password a person chose must refuse it first with `ErrPasswordTooLong`, the DAV credentials included; login never checks it. The SPA mirrors the rules in `webinterface/utils/passwordPolicy.ts`. Also `NormalizeCredentialName` (trimmed, 1–100 characters) shared by app passwords, DAV credentials and MCP tokens, and `ValidateDAVCredentialUsername` (3–50 lowercase letters `a`–`z`, nothing else; checked when a CalDAV/CardDAV credential is created; the CalDAV credential lookup relies on it and lower-cases its input).
- `repository.go` — Repository interfaces for user, refresh token, email verification, app password, OAuth connection, MCP token, and credential persistence. `ReadableCalendar` also carries `OwnerID` (the calendar's owner, whose time zone resolves floating alarms) and `Subscribed` (the alarm use case drops those calendars); neither is ever serialised. `CalendarRepository.ListAlarmCandidates(ids, from, until)` (#169) is the coarse pre-filter of `GET /alarms/upcoming`: live rows with `calendar_id IN ids AND alarm_last_at >= from AND alarm_first_at <= until` (bounds UTC, inclusive), an empty id list matches nothing without a query, and it never widens the ids (the `ListTasks` rule). `UserPreferenceRepository.ListByKey(userIDs, key)` (domain/user) loads one key for several users in one query.

### [calendar/](calendar/)

- `calendar.go` — Calendar entity (name, color, description, public sharing token). Carries `Subscribed` (story 100) and `EffectivePermission`, which caps a subscribed calendar at read-only. That helper is the ONE place the "a subscription is read-only" rule is expressed; REST, CalDAV and MCP all funnel their permission resolution through it, so a write path that already refuses `PermissionRead` needs no new code and cannot be forgotten. It caps object access only — ownership of the collection (rename, recolour, share, delete) is unaffected, and those sites compare `cal.UserID` directly. `UserID` (the owner's primary key) is `json:"-"` (P03): responses expose the owner only through the list's `owner` block (UUID + display name), never as a numeric id.
  - **Component sets (#170).** `SupportedComponents` is the comma list of what the collection stores: `VEVENT` (a calendar), `VTODO` (a task list), `VEVENT,VTODO` (mixed); a legacy `""` means both, as an absent CalDAV component set does. `SupportsComponent(cal, componentType)` is the ONE component-set rule (nil calendar: false): the CalDAV `supported-calendar-component-set` is built from it (webdav `calendarComponentSet`, which DAV PUT enforces), and the REST event writes and move, the task writes and the calendar import check it through `RequireComponent`, which returns nil or the refusal `This calendar does not store events` / `This calendar does not store tasks` (an `ErrComponentNotStored` that is also `ErrInvalidInput`, so a 400). Feed sync is exempt: subscriptions are mixed. Never compare the column yourself.
  - **Kinds (#170).** `KindEvents`/`KindTasks`/`KindBoth` (`"events"`/`"tasks"`/`"both"`) are the REST API's names for a set and are never stored. `SupportedComponentsForKind(kind)` maps a kind to its set — a closed enum compared exactly; anything else, `""` included, is an `Invalidf` 400, and defaulting an absent kind is the caller's job — and `KindOf(cal)` derives the kind from what the calendar stores (`""` is both; a calendar storing neither, which nothing writes, reports events). A set changes after create only through `CalendarRepository.UpdateSupportedComponents`.
- `calendar_object.go` — CalDAV object (iCalendar data, ETag) and its denormalized columns (summary, times, `IsAllDay`, `RecurrenceEndTime`), plus the **alarm bounds** (#169) `AlarmFirstAt` / `AlarmLastAt` (UTC, `json:"-"`, NULL without a deliverable alarm; the partial index `idx_calobj_cal_alarm (calendar_id, alarm_last_at) WHERE alarm_last_at IS NOT NULL` makes the upcoming-alarms query skip objects without alarms). The **task columns** (#170) are filled from a VTODO and empty/nil on VEVENT rows, all `json:"-"` (the API serves them through the task DTOs) and never set by callers: `Status` (upper-case, one of the `denorm_task.go` constants `TaskStatusNeedsAction`, `TaskStatusInProcess`, `TaskStatusCompleted`, `TaskStatusCancelled`), `DueAt` (DUE, else DTSTART+DURATION, UTC; a date-only due is midnight UTC; indexed), `CompletedAt` (UTC), `PercentComplete` (clamped to 0..100), `Priority` (1..9; PRIORITY 0, "undefined", is nil). For a VTODO `IsAllDay` is DUE's (else DTSTART's) value type, which the API reports as `due_all_day`. The composite index `idx_calobj_cal_comp` (`calendar_id`, `component_type`) serves the task queries. `IsEvent()` / `IsTask()` (nil-safe, exact `ComponentType`) are the kind tests the routes and use cases share: the event side answers a non-event like an unknown event, the task side a non-task like an unknown task.
- `denorm.go`, `denorm_task.go` — `PopulateDenormFieldsFromICal`, the single source of every denormalized column (`Summary`/`Description`/`Location` as plain text via `TextPropValue`; the UID raw), called by every writer (REST event and task create/update, DAV PUT, import, feed sync, the boot backfills); the ETag stays the caller's job. For a VTODO it fills the task columns (`populateTaskFields`) and clears them otherwise, so a PUT that turns a task into an event keeps no stale values. Task rules: STATUS is upper-cased; without one the task is COMPLETED when a `COMPLETED` property exists, else NEEDS-ACTION; an unknown STATUS reads NEEDS-ACTION in the column (the iCalendar keeps the raw value), so SQL filters need no special case. A malformed optional property leaves its column nil and never fails the write; a DUE that does not parse does not fall back to DTSTART+DURATION; a negative DURATION counts as malformed. Floating and DATE values are read as UTC wall time (spec R3, as for event start times), and a TZID `time.LoadLocation` cannot resolve (a custom or Windows name defined only by the object's VTIMEZONE) leaves `DueAt`/`CompletedAt` nil — the limit `StartTime` already has. `RecurrenceEndTime` is still computed for a VTODO, but it is nil for one with RRULE and no DTSTART, and for DTSTART+DUE it is the last occurrence's DTSTART (go-ical's end of a task ignores DUE); the CalDAV VTODO time-range matcher accounts for both.
- `alarm_bounds.go` — `populateAlarmBounds`, called by `PopulateDenormFieldsFromICal` after `RecurrenceEndTime` (spec §6.8): the min/max trigger instant over every deliverable alarm of every VEVENT component (masters and overrides, cancelled ones skipped) or of a VTODO master that is not done (`Status`); an absolute UTC/TZID trigger is `[t,t]`, a floating one `±14 h`, a relative one `[a+o,a+o]` (`±1 h` for nominal days, `±14 h` more for a floating/DATE anchor), a relative one on a recurring master spans the first anchor to `RecurrenceEndTime + max(o,0)` (`farFuture` when unbounded; RDATE counts, though `ExpandAlarms` does not expand it). Never fails, never depends on a zone; over-including is fine, under-including is a bug (`TestAlarmBounds_ContainExpandedInstants`). **Never add a writer of `CalendarObject.ICalData` that skips `PopulateDenormFieldsFromICal`**: the bounds would go stale and alarms would be missed.
- `text.go` — RFC 5545 TEXT (§3.3.11) at the API boundary: `UnescapeText` (`\\` `\;` `\,` `\n`/`\N` undone in ONE string — never split at an unescaped comma like go-ical's `Prop.Text`; an unknown escape or a trailing backslash is kept), `EscapeText` (go-ical's `SetText` plus CR/CRLF → `\n`), `NewTextProp` (the write helper for SUMMARY/DESCRIPTION/LOCATION) and `TextPropValue` (the read helper). Every API-facing read of those properties (the denormalized columns, `ToEventInstance`'s master/override text, the import's reported summary) and every REST/MCP write (event and task create/update) goes through them, so the API's text is plain and a round trip adds no backslash. The UID is not text in this sense and stays raw.
- `task.go` — the task rules the use cases and the repository share (#170): `TaskFilterOpen`/`TaskFilterCompleted`/`TaskFilterAll` (the `status` filter values) and `TaskDoneStatuses()` — COMPLETED and CANCELLED, the ONE cancelled rule, so `?status=completed` and the `completed` count always agree (open = everything else, a NULL or empty status included). `(*CalendarObject).TaskDetails()` reads what has no column from the iCalendar: the master's DTSTART (UTC) and its value type, the RRULE, and `Recurring` (an RRULE, also an unparseable one, or an RDATE on the master); zero value for undecodable data, so one bad object never breaks a list. `TaskMaster(cal)` is the VTODO a task is read from and edited in: the first without `RECURRENCE-ID`, else the first. `TaskDay`/`TaskDayOf(asOf)` is the summary's "now" and "today", read in `asOf`'s own fixed UTC offset (never the server's zone, a 24-hour day): an open timed task is overdue once due before now, an all-day one once its date is before today's date; due today = on today's date; the two overlap for a timed task due earlier today. A floating due is compared as UTC wall time (R3, a known approximation).
- `vtimezone.go` — `SyncVTimezones` (one VTIMEZONE per TZID an object references, unused ones dropped, a client's own definition kept) and `GenerateVTimezone`, which builds one from Go's tz data: a fixed window from 1970 (earlier for older events) to 2100, yearly transitions compressed into `RRULE`s such as `BYMONTH=3;BYDAY=-1SU`, open-ended past 2100. The window is fixed so every object of a zone carries the identical block (the calendar export keeps one per TZID). `LoadEventLocation` refuses `Local`.
- `alarm.go` — VALARM parsing and trigger computation (#169, pure, no I/O). `ParseAlarms(comp)` returns one `AlarmSpec` per VALARM child and never fails a write: an unreadable TRIGGER is `Valid=false` (still listed). `parseAlarmDuration` is its own RFC 5545 parser (go-ical's turns `D`/`W` into 24 h and accepts a bare `P`); 400-day cap. `ComponentTriggerBases` gives the START/END anchors of a VEVENT or VTODO (VTODO END is DUE, never `componentEnd`); `AlarmSpec.TriggerAt(start, end, ownerLoc)` returns the UTC instant. A TZID/`Z` anchor applies `D`/`W` as nominal days in its zone; a floating or DATE anchor (`TriggerBase.Wall`, a UTC-wall value, R3) gets the WHOLE duration in wall time first and is only then placed in the owner's zone (`time.Date`; nil zone = UTC) — never place first and add hours. `ACKNOWLEDGED` is ignored (D18). Delivered actions: DISPLAY, AUDIO, none.
- `event.go` — Event entity (title, dates, recurrence, attendees). `ExpandRecurringEvent` is built on the internal iterator `forEachOccurrence(cal, start, end, fn)` (#169), which visits `Occurrence{Start, End, Wall, RecurrenceID, Master, Override}` (generated beat, single master, override that replaced a beat, stray override) under the per-object caps of `recurrence.go`; `Wall` = the DTSTART is a DATE or floating (UTC-wall values, R3). Its output is pinned byte for byte by `event_golden_test.go` (`testdata/expand_recurring_event_golden.json`; regenerate only on purpose with `UPDATE_GOLDEN=1`). RDATE is NOT expanded (pre-existing gap: an RDATE-only event expands to its DTSTART only, RRULE+RDATE series miss the extras).
- `alarm_expand.go` — `ExpandAlarms(obj, from, until, ownerLoc)` (#169): every deliverable alarm with its trigger in `[from, until]`, at most `AlarmInstanceCap` (500) per object (`capped` only when a 501st exists). Master VALARMs per generated occurrence; an override uses ONLY its own VALARMs (none = no alarm for that beat); a stray override is an occurrence of its own; an absolute trigger fires once per component (master `rid=""`, override its own rid); EXDATE yields nothing; STATUS:CANCELLED silences that component (a cancelled master's beats, but a non-cancelled override still delivers). Tasks are never expanded: master's DUE/DTSTART once, nothing when the `Status` column is in `TaskDoneStatuses()`. The iterator window is widened by the series' relative offsets (days as 24 h + 1 h slack, ±14 h when any series is floating/DATE). `AlarmKey(uid, rid, triggerAt)` = hex of the first 16 bytes of SHA-256(`calcard-alarm-v1|<trigger UTC 20060102T150405Z>|<rid>|<uid>`), no VALARM index (D22): same-instant VALARMs of one component/occurrence collapse into one instance carrying the lowest index. The key match is the join (D19): the key `ExpandAlarms` computes is what an acknowledgement stores, so the rid is exactly the key the expansion matches overrides with (`RecurrenceIDKeyFromProp(prop, docLoc)`) and any change to the key inputs needs a new prefix version. The calendar is not part of the key. `AlarmInstance` also carries `Location` (override-aware like `Summary`) and `ZoneDependent` (the trigger came from a floating or DATE anchor, or a floating absolute trigger, so the owner's zone mattered): the upcoming use case logs the zone fallback only for those.
- `alarm_ack.go` — `AlarmAcknowledgement` (#169), table `alarm_acknowledgements`: composite primary key `(user_id, alarm_key)` (`alarm_key` is the §6.7 hash that already contains the trigger instant, so no trigger column), `acknowledged_at` set by the use case in UTC (never `autoCreateTime`), no foreign key. `AlarmAcknowledgementRepository` lives in `repository.go`.
- `alarm_write.go` — writing VALARMs in place (#169, story 11, pure). `ReminderInput` (`OffsetSeconds *int64` XOR `At *time.Time`), `ReminderKind` (`event` = `RELATED=START`, `task` = `RELATED=END`), `AlarmSpec.Editable(kind)` (the one definition of the editable rule: valid, action DISPLAY/AUDIO/absent, no REPEAT or snooze, relative to the kind's anchor or absolute and non-floating; `dto.newReminderResponse` uses it), `CheckReminderShape`/`CheckReminderRanges` (the 400 texts as `ErrReminder*`), `UnmatchedReminders` (the entries no stored editable VALARM matches: the only ones the range checks apply to) and `ApplyReminders(comp, desired, kind) (changed, appended)`: greedy multiset match in document order, matched kept untouched, unmatched editable removed, non-editable never touched, new VALARMs appended after the existing children with `UID` uuid v4. `FormatAlarmDuration` is the canonical writer (`P{n}W` for whole weeks, else `P{d}DT{h}H{m}M{s}S` without zero parts, `PT0S`; never go-ical's `SetDuration`). `ShiftAbsoluteTriggers` follows in story 13.
- `ShiftAbsoluteTriggers(comp, n, ownerLoc, skip)` and `DatePropDay(prop)` (#169, story 13, in `alarm_write.go`): the all-day date shift of D23. `DatePropDay` is the day number of a DATE property (false for a date-time), the difference of two is the moved days. `ShiftAbsoluteTriggers` rewrites every absolute, non-floating, not-skipped VALARM TRIGGER of comp to `TRIGGER;VALUE=DATE-TIME:<UTC>Z`, n calendar days later at the same local time in `ownerLoc` (nil = UTC), and touches nothing else. Only the REST/MCP update use cases call it.
- `subscription.go` — `CalendarSubscription` (story 100): the remote iCalendar feed behind a subscribed calendar, plus the status derivation, the allowed refresh-interval set, and the success/failure state machine (`RecordSuccess` / `RecordFailure`, exponential backoff anchored to the subscription's own interval, capped at 24h, auto-disable after N failures). A sidecar to `Calendar` rather than columns on it: every field here is meaningless for an ordinary calendar.
- `sync_changelog.go` — WebDAV-Sync change tracking.
- `validation.go` — Calendar/event validation.
- `errors.go` — `ErrNotFound`: a missing calendar and one the caller may not access are the same error (and the same 404), so no endpoint leaks existence (F12). `ErrInvalidInput` / `Invalidf` mark a request the caller can correct (400, message kept verbatim); `ErrConflict` / `Conflictf` (#170) a well-formed request the calendar's state refuses (409, message kept verbatim — a PATCH that would narrow the component set); `ErrComponentNotStored` (#170, from `RequireComponent`) a write into a calendar that does not store that component, also an `ErrInvalidInput`. Every other calendar error is a server failure (500, F28). `validation.go` returns `Invalidf` errors.
- `repository.go` — Repository interfaces for calendars, events, sync, and calendar subscriptions. `CalendarRepository.ReplaceFeedObjects` is the transactional feed diff the subscription sync uses — and the only writer permitted on a subscribed calendar. `DeleteCalendarObject` soft-deletes; `HardDeleteCalendarObject` (#170, every task DELETE: the REST route and a DAV DELETE of a VTODO) removes the row for good with the same `deleted` change-log row, and is `ErrNotFound` with nothing recorded when no live row is left (already gone, or only a soft-deleted tombstone). `UpdateCalendarObjectIfETag(obj, loadedETag)` is the task edits' write: one conditional `UPDATE … WHERE id = ? AND e_tag = ?` with explicit columns (never `Save`, whose INSERT fall-back resurrects a row a concurrent DELETE removed), `ErrNotFound` when no live row is left and `ErrETagMismatch` when another writer changed it first, neither recording a change. `UpdateSupportedComponents(ctx, id, set)` (#170) is the only way to change `supported_components` after create (the widen-only PATCH, the narrowing migration): the column plus a change-log anchor (new ctag/sync token) in one transaction, `ErrNotFound` for a missing calendar; `UpdateMetadata` cannot write it. `GetEventCount` counts events only. Task queries (#170) — each caller resolves the calendars the user may read, the repository trusts the ids and never widens them, and an empty id list matches nothing: `TaskQuery` + `ListTasks` (one page of VTODOs plus the total; status filter, literal case-insensitive text match, half-open due bounds `[DueAfter, DueBefore)` in UTC that an undated task never matches; order due date, priority, created, id with undated and unprioritised tasks last); `ReadableCalendar` + `ListReadableCalendarIDs(userID)` (every calendar the user can read — own, subscribed included, and shared — in ONE query, as id, UUID, name, colour and component set; it carries no permission, so never authorise a write with it); `TaskCount`/`TaskCounts` + `CountTasks(ids, asOf)` (open, overdue, due today and completed per calendar and in total at `TaskDayOf(asOf)`, ONE grouped query; a calendar without tasks has no entry).

## Design Constraints

- **Zero Dependencies**: This package must not import anything from `usecase`, `adapter`, or `infrastructure`.
- **Pure Go**: Should only depend on the Go standard library (and potentially very minimal utility libraries if absolutely necessary).
- **Stability**: This is the most stable part of the codebase; changes here usually trigger changes in all other layers.
