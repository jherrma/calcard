# Domain Layer

This is the innermost layer of the application. It contains the core business logic and state of the application, completely independent of any external frameworks, databases, or UI.

## Responsibility

The domain layer defines:

- **Entities**: Business models representing the core concepts.
- **Interfaces**: Crucial abstractions for data persistence and external services.
- **Domain Logic**: Business rules that are intrinsic to the data itself (e.g., password hashing methods on the `User` model).

## Subdirectories

### [user/](user/)

- `user.go` — Core user entity (profile data, security status, password hashing). `TokensValidAfter` (`json:"-"`, nil = never revoked) invalidates every access token issued before it; `AcceptsAccessTokenIssuedAt` is the single rule (a token issued at exactly the marker is accepted, so the replacement token change-password mints right after setting it survives). `DeletedIdentityPrefix` (`deleted:`) builds the tombstone a deleted account's e-mail and username are replaced with.
- `refresh_token.go` — Opaque tokens for session persistence, linked to users and client context (User Agent, IP).
- `email_verification.go` — Email verification token model.
- `app_password.go` — Application-specific passwords for DAV client access. The only scopes are `ScopeCalDAV` / `ScopeCardDAV` (`AppPasswordScopes()`, also the default for a create without scopes).
- `caldav_credential.go` — CalDAV-specific access credentials.
- `carddav_credential.go` — CardDAV-specific access credentials.
- `mcp_token.go` — Long-lived bearer credential for the `/mcp` endpoint (story 104). Unlike the DAV credentials it stores a **unique-indexed SHA-256** of a 256-bit random secret rather than a bcrypt hash: an MCP client presents only the opaque token, so it must be findable from that string alone, which a per-row salted hash cannot do. `TokenPrefix` is the only cleartext fragment, kept so a shown-once token stays recognizable in the settings list.
- `validation.go` — User input validation logic, incl. `ValidatePassword` — the policy for a NEW account password: 8 to `MaxPasswordBytes` (72) **bytes**, an upper-case letter, a lower-case letter, a digit and a punctuation/symbol character, by Unicode class. The maximum is bcrypt's (x/crypto refuses longer input with `bcrypt.ErrPasswordTooLong` rather than truncating), so every site that hashes a password a person chose must refuse it first with `ErrPasswordTooLong`, the DAV credentials included; login never checks it. The SPA mirrors the rules in `webinterface/utils/passwordPolicy.ts`. Also `NormalizeCredentialName` (trimmed, 1–100 characters) shared by app passwords, DAV credentials and MCP tokens, and `ValidateDAVCredentialUsername` (3–50 lowercase letters `a`–`z`, nothing else; checked when a CalDAV/CardDAV credential is created; the CalDAV credential lookup relies on it and lower-cases its input).
- `repository.go` — Repository interfaces for user, refresh token, email verification, app password, OAuth connection, MCP token, and credential persistence.

### [calendar/](calendar/)

- `calendar.go` — Calendar entity (name, color, description, public sharing token). Carries `Subscribed` (story 100) and `EffectivePermission`, which caps a subscribed calendar at read-only. That helper is the ONE place the "a subscription is read-only" rule is expressed; REST, CalDAV and MCP all funnel their permission resolution through it, so a write path that already refuses `PermissionRead` needs no new code and cannot be forgotten. It caps object access only — ownership of the collection (rename, recolour, share, delete) is unaffected, and those sites compare `cal.UserID` directly. `UserID` (the owner's primary key) is `json:"-"` (P03): responses expose the owner only through the list's `owner` block (UUID + display name), never as a numeric id.
  - **Component sets (#170).** `SupportedComponents` is the comma list of what the collection stores: `VEVENT` (a calendar), `VTODO` (a task list), `VEVENT,VTODO` (mixed); a legacy `""` means both, as an absent CalDAV component set does. `SupportsComponent(cal, componentType)` is the ONE component-set rule (nil calendar: false): the CalDAV `supported-calendar-component-set` is built from it (webdav `calendarComponentSet`, which DAV PUT enforces), and the REST event writes and move, the task writes and the calendar import check it through `RequireComponent`, which returns nil or the refusal `This calendar does not store events` / `This calendar does not store tasks` (an `ErrComponentNotStored` that is also `ErrInvalidInput`, so a 400). Feed sync is exempt: subscriptions are mixed. Never compare the column yourself.
  - **Kinds (#170).** `KindEvents`/`KindTasks`/`KindBoth` (`"events"`/`"tasks"`/`"both"`) are the REST API's names for a set and are never stored. `SupportedComponentsForKind(kind)` maps a kind to its set — a closed enum compared exactly; anything else, `""` included, is an `Invalidf` 400, and defaulting an absent kind is the caller's job — and `KindOf(cal)` derives the kind from what the calendar stores (`""` is both; a calendar storing neither, which nothing writes, reports events). A set changes after create only through `CalendarRepository.UpdateSupportedComponents`.
- `calendar_object.go` — CalDAV object (iCalendar data, ETag) and its denormalized columns (summary, times, `IsAllDay`, `RecurrenceEndTime`). The **task columns** (#170) are filled from a VTODO and empty/nil on VEVENT rows, all `json:"-"` (the API serves them through the task DTOs) and never set by callers: `Status` (upper-case, one of the `denorm_task.go` constants `TaskStatusNeedsAction`, `TaskStatusInProcess`, `TaskStatusCompleted`, `TaskStatusCancelled`), `DueAt` (DUE, else DTSTART+DURATION, UTC; a date-only due is midnight UTC; indexed), `CompletedAt` (UTC), `PercentComplete` (clamped to 0..100), `Priority` (1..9; PRIORITY 0, "undefined", is nil). For a VTODO `IsAllDay` is DUE's (else DTSTART's) value type, which the API reports as `due_all_day`. The composite index `idx_calobj_cal_comp` (`calendar_id`, `component_type`) serves the task queries. `IsEvent()` / `IsTask()` (nil-safe, exact `ComponentType`) are the kind tests the routes and use cases share: the event side answers a non-event like an unknown event, the task side a non-task like an unknown task.
- `denorm.go`, `denorm_task.go` — `PopulateDenormFieldsFromICal`, the single source of every denormalized column (`Summary`/`Description`/`Location` as plain text via `TextPropValue`; the UID raw), called by every writer (REST event and task create/update, DAV PUT, import, feed sync, the boot backfills); the ETag stays the caller's job. For a VTODO it fills the task columns (`populateTaskFields`) and clears them otherwise, so a PUT that turns a task into an event keeps no stale values. Task rules: STATUS is upper-cased; without one the task is COMPLETED when a `COMPLETED` property exists, else NEEDS-ACTION; an unknown STATUS reads NEEDS-ACTION in the column (the iCalendar keeps the raw value), so SQL filters need no special case. A malformed optional property leaves its column nil and never fails the write; a DUE that does not parse does not fall back to DTSTART+DURATION; a negative DURATION counts as malformed. Floating and DATE values are read as UTC wall time (spec R3, as for event start times), and a TZID `time.LoadLocation` cannot resolve (a custom or Windows name defined only by the object's VTIMEZONE) leaves `DueAt`/`CompletedAt` nil — the limit `StartTime` already has. `RecurrenceEndTime` is still computed for a VTODO, but it is nil for one with RRULE and no DTSTART, and for DTSTART+DUE it is the last occurrence's DTSTART (go-ical's end of a task ignores DUE); the CalDAV VTODO time-range matcher accounts for both.
- `text.go` — RFC 5545 TEXT (§3.3.11) at the API boundary: `UnescapeText` (`\\` `\;` `\,` `\n`/`\N` undone in ONE string — never split at an unescaped comma like go-ical's `Prop.Text`; an unknown escape or a trailing backslash is kept), `EscapeText` (go-ical's `SetText` plus CR/CRLF → `\n`), `NewTextProp` (the write helper for SUMMARY/DESCRIPTION/LOCATION) and `TextPropValue` (the read helper). Every API-facing read of those properties (the denormalized columns, `ToEventInstance`'s master/override text, the import's reported summary) and every REST/MCP write (event and task create/update) goes through them, so the API's text is plain and a round trip adds no backslash. The UID is not text in this sense and stays raw.
- `task.go` — the task rules the use cases and the repository share (#170): `TaskFilterOpen`/`TaskFilterCompleted`/`TaskFilterAll` (the `status` filter values) and `TaskDoneStatuses()` — COMPLETED and CANCELLED, the ONE cancelled rule, so `?status=completed` and the `completed` count always agree (open = everything else, a NULL or empty status included). `(*CalendarObject).TaskDetails()` reads what has no column from the iCalendar: the master's DTSTART (UTC) and its value type, the RRULE, and `Recurring` (an RRULE, also an unparseable one, or an RDATE on the master); zero value for undecodable data, so one bad object never breaks a list. `TaskMaster(cal)` is the VTODO a task is read from and edited in: the first without `RECURRENCE-ID`, else the first. `TaskDay`/`TaskDayOf(asOf)` is the summary's "now" and "today", read in `asOf`'s own fixed UTC offset (never the server's zone, a 24-hour day): an open timed task is overdue once due before now, an all-day one once its date is before today's date; due today = on today's date; the two overlap for a timed task due earlier today. A floating due is compared as UTC wall time (R3, a known approximation).
- `vtimezone.go` — `SyncVTimezones` (one VTIMEZONE per TZID an object references, unused ones dropped, a client's own definition kept) and `GenerateVTimezone`, which builds one from Go's tz data: a fixed window from 1970 (earlier for older events) to 2100, yearly transitions compressed into `RRULE`s such as `BYMONTH=3;BYDAY=-1SU`, open-ended past 2100. The window is fixed so every object of a zone carries the identical block (the calendar export keeps one per TZID). `LoadEventLocation` refuses `Local`.
- `event.go` — Event entity (title, dates, recurrence, attendees).
- `subscription.go` — `CalendarSubscription` (story 100): the remote iCalendar feed behind a subscribed calendar, plus the status derivation, the allowed refresh-interval set, and the success/failure state machine (`RecordSuccess` / `RecordFailure`, exponential backoff anchored to the subscription's own interval, capped at 24h, auto-disable after N failures). A sidecar to `Calendar` rather than columns on it: every field here is meaningless for an ordinary calendar.
- `sync_changelog.go` — WebDAV-Sync change tracking.
- `validation.go` — Calendar/event validation.
- `errors.go` — `ErrNotFound`: a missing calendar and one the caller may not access are the same error (and the same 404), so no endpoint leaks existence (F12). `ErrInvalidInput` / `Invalidf` mark a request the caller can correct (400, message kept verbatim); `ErrConflict` / `Conflictf` (#170) a well-formed request the calendar's state refuses (409, message kept verbatim — a PATCH that would narrow the component set); `ErrComponentNotStored` (#170, from `RequireComponent`) a write into a calendar that does not store that component, also an `ErrInvalidInput`. Every other calendar error is a server failure (500, F28). `validation.go` returns `Invalidf` errors.
- `repository.go` — Repository interfaces for calendars, events, sync, and calendar subscriptions. `CalendarRepository.ReplaceFeedObjects` is the transactional feed diff the subscription sync uses — and the only writer permitted on a subscribed calendar. `DeleteCalendarObject` soft-deletes; `HardDeleteCalendarObject` (#170, every task DELETE: the REST route and a DAV DELETE of a VTODO) removes the row for good with the same `deleted` change-log row, and is `ErrNotFound` with nothing recorded when the row is already gone. `UpdateSupportedComponents(ctx, id, set)` (#170) is the only way to change `supported_components` after create (the widen-only PATCH, the narrowing migration): the column plus a change-log anchor (new ctag/sync token) in one transaction, `ErrNotFound` for a missing calendar; `UpdateMetadata` cannot write it. `GetEventCount` counts events only. Task queries (#170) — each caller resolves the calendars the user may read, the repository trusts the ids and never widens them, and an empty id list matches nothing: `TaskQuery` + `ListTasks` (one page of VTODOs plus the total; status filter, literal case-insensitive text match, half-open due bounds `[DueAfter, DueBefore)` in UTC that an undated task never matches; order due date, priority, created, id with undated and unprioritised tasks last); `ReadableCalendar` + `ListReadableCalendarIDs(userID)` (every calendar the user can read — own, subscribed included, and shared — in ONE query, as id, UUID, name, colour and component set; it carries no permission, so never authorise a write with it); `TaskCount`/`TaskCounts` + `CountTasks(ids, asOf)` (open, overdue, due today and completed per calendar and in total at `TaskDayOf(asOf)`, ONE grouped query; a calendar without tasks has no entry).

### [addressbook/](addressbook/)

- `address_object.go` — CardDAV address object (vCard data, ETag).
- `photo.go` — Contact photo model.
- `sync_changelog.go` — WebDAV-Sync change tracking for contacts.
- `repository.go` — Repository interfaces for address books, contacts, and sync.

### [contact/](contact/)

### [sharing/](sharing/)

## Design Constraints

- **Zero Dependencies**: This package must not import anything from `usecase`, `adapter`, or `infrastructure`.
- **Pure Go**: Should only depend on the Go standard library (and potentially very minimal utility libraries if absolutely necessary).
- **Stability**: This is the most stable part of the codebase; changes here usually trigger changes in all other layers.
