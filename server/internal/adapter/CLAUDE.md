# Adapter Layer

The adapter layer is responsible for translating data between the application's internal layers (domain and use case) and the outside world. It follows the **Clean Architecture** pattern by implementing the "Port" interfaces defined in the domain layer.

## Subdirectories

### [http/](http/)

- **Purpose**: Handles HTTP/REST communication using the Fiber framework.
- **Key Components**:
  - **Handlers**: One handler per domain area — `auth_handler.go`, `oauth_handler.go`, `user_handler.go`, `system_handler.go`, `calendar_handler.go`, `event_handler.go`, `task_handler.go` (tasks, #170: the per-list routes under `/calendars/:calendar_id/tasks` and the cross-list `GET /tasks` and `GET /tasks/summary`, which take the user from the JWT and answer 401 themselves should the route ever lose `Authenticate`; every route is described in `server/CLAUDE.md`, "Tasks (#170)"), `addressbook_handler.go`, `contact_handler.go`, `calendar_share_handler.go`, `addressbook_share_handler.go`, `calendar_public_handler.go`, `public_calendar_handler.go`, `app_password_handler.go`, `caldav_credential_handler.go`, `carddav_credential_handler.go`, `import_handler.go`, `backup_handler.go`, `mcp_token_handler.go` (MCP access tokens, #104), `subscription_handler.go` (remote calendar subscriptions, story 100), `health.go`, `about_handler.go` (open-source attribution), `search_handler.go` (unified search, #156).
  - **DTOs** (`dto/`): Data Transfer Objects for auth, user, contact, addressbook, event, task (`TaskResponse`, #170: UTC `due`, `due_date` for an all-day task, lower-case `status`; `CreateTaskRequest`, dates as strings so an all-day task can send `YYYY-MM-DD`; `UpdateTaskRequest` with `OptionalField[T]`, which tells an absent key from an explicit null, for the five removable fields; `TaskWithCalendarResponse`, a `TaskResponse` plus `calendar_name`/`calendar_color`, for the cross-list `GET /api/v1/tasks`, built by `NewTaskWithCalendarResponse`, which MCP `list_tasks` renders through too; `TaskSummaryResponse`, the counts of `GET /api/v1/tasks/summary`, `by_calendar` never null), reminder (`ReminderResponse`, #169, `dto/reminder_dto.go`: the `reminders` array of `EventResponse` and `TaskResponse`, built by `NewReminderResponses(specs, kind)`, never null; MCP `list_tasks` and the other task tools gained it through `TaskResponse`) and credentials.
  - **Calendar object access** (`calendar_access.go`): `resolveCalendar`, `calendarPermission` (both, like `objectPermission`, return a storage failure as an error that callers answer with `accessError`, a 500 with the cause logged, never as a 404) (subscription cap via `calendar.EffectivePermission`), `objectPermission` (the object must live in the URL's `:calendar_id` and pass the route's kind test, `IsEvent` or `IsTask`, else one 404), `canWrite`, `ifMatchOK` — shared by the event and task handlers, never copied. The task write routes on an existing task (PATCH, DELETE, `…/complete`, `…/uncomplete`, #170) run them through `TaskHandler.writableTask` in the order 404 "Task not found" → 403 → 412 before any body or use case, and map use-case errors with `taskWriteError` (`ErrNotFound` 404, `ErrRecurringNotSupported` 409, `ErrInvalidInput` 400, else a logged generic 500). The event write routes (PATCH, DELETE, move) map theirs with `eventWriteError` (`ErrNotFound` 404 "Event not found", `ErrInvalidInput` 400, else a 500 with the route's own text); the task list routes read `limit`/`offset` with `pageQuery`.
  - **Middleware**: `auth_middleware.go` (JWT verification, then the per-user revocation check `User.AcceptsAccessTokenIssuedAt` — P02), `rate_limiter.go` (the auth endpoints' per-IP / per-e-mail Fiber limiters, and `FailedAuthLimiter` for DAV Basic auth, #193: counts only settled failed credential checks, per identifier only (no per-IP bucket: behind a reverse proxy every client shares the proxy's IP); a check in flight counts nothing, so concurrent correct logins are never refused for it, and checks in flight are capped separately at 2×max per identifier; not a Fiber limiter because those judge by the final status, which on `/dav` is the DAV handler's 404/412).
  - **Base URL**: `base_url.go` — `RequestBaseURL(c, cfg)` returns `cfg.BaseURL` or, when it is unset, the origin the request came in on (Host header; `X-Forwarded-Proto`/`-Host` only with `CALDAV_TRUST_FORWARDED_HEADERS`). Use it **only** for URLs returned to the caller of the same request (app-password `server_url`, calendar `public_url`). E-mail links and OAuth redirect URIs must keep using `cfg.BaseURL` — config validation requires it whenever SMTP or OAuth is configured — or a forged Host header poisons a password-reset link.
  - **Responses**: `response.go` — `SuccessResponse()` wraps a payload in `{ "status": "ok", "data": ... }`; `ErrorResponse()` writes `{ "status": "error", "message" }`. Only the auth, user, system, app-password, about and health handlers use the success envelope. Calendar, event, address book, contact, sharing, public-calendar, CalDAV/CardDAV-credential, import, MCP-token, search, subscription and OAuth-provider-list handlers return raw JSON. Some of the raw ones answer errors as `{ "error": ... }`. Match the existing shape of an area; changing one breaks the SPA and API clients.
  - **Not found = no access** (F12): calendar use cases return `calendar.ErrNotFound` for a missing calendar AND for one the caller does not own; `calendar_handler.go`'s `calendarError` (also used by the calendar import) turns it into the same 404 body GET gives. An unknown `:share_id` is `sharing.ErrCalendarShareNotFound` → 404. Never map a lookup failure to 400, and never give "not yours" a message of its own — that leaks existence.
  - **Typed calendar errors** (F28): a rejected request is `calendar.ErrInvalidInput` (build it with `calendar.Invalidf`, whose message is the bare text) → 400 with that message; a request the calendar's state refuses is `calendar.ErrConflict` (`calendar.Conflictf`, #170: PATCH narrowing the component set) → 409 with that message (MCP `calendarToolError`: the same message as a tool error); anything else is a server failure → 500 with a generic body (`"Internal server error"`, or `{"error":"internal_error"}` on the share/public-link routes via `calendarSubresourceError`) and the cause logged with `slog.Error`. The calendar is resolved and authorised before the body is read (PATCH, DELETE, import), so a bad body never turns the 404 into a 400. `CalendarRepository.GetByUUID`/`GetByID` report a missing row as `calendar.ErrNotFound`; any other lookup error is a 500, not a 404.

### [mcp/](mcp/)

- **Purpose**: Model Context Protocol server (story 104) — a JSON-RPC 2.0 tool/resource surface over Streamable HTTP at `/mcp`, so an AI assistant can read and manage the caller's calendars, tasks and contacts.
- **Key Components**:
  - `protocol.go` — JSON-RPC and MCP message types, protocol-version negotiation, the handshake `instructions` handed to the model.
  - `errors.go` — JSON-RPC error codes and response constructors, plus `toolInternalError` / `resourceInternalError`: the ONLY way a tool or resource reports a failure the caller cannot fix. The caller gets "An internal server error stopped <tool>. The details were logged on the server; try again later." (`resources/read` for resources) and the cause goes to `slog.Error` (F28 over MCP). Only validation (the use cases' typed errors: `calendar.ErrInvalidInput`, `event.ErrInvalidInput`, `addressbookuc.ErrNameRequired`, …), permission and not-found answers carry their own text — never `"Failed to …: " + err.Error()`, which put driver text and table names into the model's context.
  - `args.go` — `decodeArgs`, which every tool calls first: arguments the tool's struct does not declare are refused (`Unknown argument "titel"; the tool did not run. Accepted arguments: …`), as is a wrongly typed one, both as tool errors (`isError`) so the model can correct itself. Names are matched exactly — `encoding/json`, even with `DisallowUnknownFields`, accepts `CALENDAR_ID` for `calendar_id`. A tool's argument struct must list exactly its schema's properties, in schema order (`TestEveryToolRejectsUnknownArguments` compares them). A nullable argument (`dto.OptionalField[T]`, the five removable fields of `update_task`, #170) is described by its inner type plus null (`Argument "priority" must be an integer or null, got a string; …`); the refused argument is found by decoding each one alone, never read off `UnmarshalTypeError.Field`. Only `arguments` is strict: the `tools/call` params stay lenient so `_meta` next to `arguments` keeps working.
  - `server.go` — `Deps` (the use cases the tools delegate to), the tool registry, and the method dispatcher. `arguments` that are not a JSON object are a `-32602` protocol error.
  - `handler.go` — Fiber transport: bearer authentication (MCP token or JWT; a JWT gets the same revocation check as the REST middleware), `POST` (JSON-RPC, single or batch), `GET` (manifest or SSE stream), `DELETE` (terminate session).
  - `session.go` — In-memory `Mcp-Session-Id` store. Sessions are bound to a user, so a leaked id cannot be used by another account.
  - `access.go` — `callContext` plus the permission helpers, mirroring the HTTP handlers exactly. `resolveOwnedAddressBook` is the mirror of `AddressBookHandler.resolveOwnedAddressBookID` (owner-only, compared on `UserID`); the `resolveCalendar`/`calendarPermission` pair applies the subscription cap and is for object access only. `eventPermission` answers an object that is not an event (`CalendarObject.IsEvent`; a task, #170) with `PermissionNone` before any permission check, so `update_event`/`delete_event` give a task's id the unknown-id text `No event with id <id> is readable by you.`; both also map the use cases' `eventuc.ErrNotFound` to that text (a CalDAV PUT can turn an event into a task under the same UUID). `taskPermission` is its mirror for the task tools (#170): the object must be a task (`CalendarObject.IsTask`) in a calendar the caller can read, else `No task with id <id> is readable by you.` before any other check (an event's UUID on a read share included); it returns the task's own calendar with the capped permission (`calendarAccess`). `loadCalendar` is the REST handlers' `resolveCalendar` + `calendarPermission` (create_task).
  - `tools_calendar.go`, `tools_contact.go`, `tools_scheduling.go`, `tools_collection.go`, `tools_task.go` — the 26 advertised tools. `tools_collection.go` holds `create_`/`update_`/`delete_calendar` and `…_address_book`: owner-only like REST (unknown, foreign and shared collections get one identical "not owned by you" answer), the deletes take the REST `confirmation: "DELETE"` literal and say in their descriptions that they are permanent, invalid input answers with the use case's bare message, and any other failure is a generic internal error with the cause only in the log (F28) — the rule every tool follows. `find_free_slots` names the calendar it could not read (the caller just listed it), never the error. Every calendar view (`list_calendars`, `calendars://list`, the `create_`/`update_calendar` output) carries the derived `kind` (#170), or a task list would read like an empty calendar; `create_calendar` takes `kind` (default events) and `update_calendar` a widen-only one, both decided by the calendar use cases (narrowing is `calendar.ErrConflict` through `calendarToolError`). The event tools read events only, and `find_free_slots` leaves task lists out of its default calendars. `tools_task.go` (#170) holds `list_tasks`, `create_task`, `update_task`, `complete_task`, `uncomplete_task`, `delete_task` and `get_task_summary`, each tool's `Tool` definition a package-level var (`listTasksTool`, …) right above its handler, so the schema sits next to the argument struct it must match: each decodes its arguments, checks access (`writableTask` = `task_id is required.`, `taskPermission`, then read-only; `complete_task`, `uncomplete_task` and `delete_task` open with `writableTaskArgument`, the strict decode of `task_id` plus `writableTask`; `create_task`: `loadCalendar`), makes ONE call to the use case the REST task route uses (`Deps.Task*`, the same instances, built once in `routes.go`) and renders with the REST DTOs (`dto.NewTaskResponse`, `dto.TaskWithCalendarResponse`, `dto.NewTaskSummaryResponse`), so a task reads byte-for-byte as REST answers it. Use-case errors go through `taskToolError` (`ErrNotFound` the unknown-task text, `ErrRecurringNotSupported` and `ErrInvalidInput` their own text, `ErrCalendarNotFound` the unknown-calendar text, else `toolInternalError`). Only `list_tasks`' bounds and `get_task_summary`'s `as_of` are parsed here (`time.RFC3339`, an offset required); `list_tasks` defaults `limit` to 50.
  - `resources.go` — `calendars://list`, `contacts://list`, `calendars://{id}/events`, `contacts://{id}`. `resources/list` enumerates no events resource for a task list (`kind` tasks, #170); its URI still reads as an empty list. The list resources render through the same functions as `list_calendars` / `list_address_books`; a storage failure is a `-32603` with the generic text, not "not found".
  - Tests break the SQLite schema under the real use cases (`failWrites` / `hideTable` in `setup_test.go`); `internal_errors_test.go` and `args_test.go` walk the tool registry, so a new tool without a storage-failure case or a strict decode fails the tests.
- **Invariant**: this package owns **no** persistence, queries or permission logic. Every tool calls the same use case the REST handler does and resolves access through the same repository methods, so MCP can never reach data REST would refuse. A tool that reaches past a use case is a bug, not an optimization.

### [repository/](repository/)

- **Purpose**: Implements persistence logic for domain entities using GORM.
- **Key Components**:
  - `user_repo.go` — User persistence. `Delete` soft-deletes the user row but first hard-deletes everything the account owns or was granted, via `PurgeAccountData` (`account_purge.go`, F18). It then rewrites the e-mail and username to `deleted:<uuid>` (a tombstone), because the unique indexes cover soft-deleted rows (F19); `Count` is `Unscoped` so deleted accounts still keep first-run setup closed. `CompletePasswordReset` saves the new password and, in one transaction, ends every session and deletes the account's credentials (`purgeAccountCredentials`).
  - `user_preference_repo.go` — Preference rows, unique on `(user_id, key)` (`idx_user_pref_key`). `Upsert` overwrites; `InsertIfAbsent` (`ON CONFLICT DO NOTHING`, the #169 set-if-empty write) and `ReplaceValueIf` (`UPDATE … WHERE value = old`) never clobber a concurrent write. HTTP: `PUT /api/v1/users/me/preferences/timezone-default` (`UserHandler.SetDefaultTimezone`, body `{timezone}`, `{status,data:{timezone}}`, 400 `Invalid request body` / the validation sentence, 401, 404 `User not found`).
  - `account_purge.go` — `PurgeAccountData`: the account-deletion cascade — the shares granted TO the account, then the account's calendars and address books through the collection cascade below, then its app passwords, DAV credentials, MCP tokens, OAuth links (`accountCredentials`, which a password reset deletes too) and preferences. A table that gains a `user_id` must be added here, or deleted accounts leak it; a new kind of credential goes into `accountCredentials`. The data migration `purgeDeletedAccounts` runs the same cascade for accounts deleted before it existed.
  - `collection_purge.go` — the collection cascade: what deleting a calendar or address book removes, permanently and in the caller's transaction. Calendar: shares, subscription, objects, change log (`calendarContents`), then the calendar row (its public token lives on it). Address book: shares, contact photos (matched through the contacts), contacts, change log, then the book row. Children before parents, because SQLite (`_foreign_keys=on`) and PostgreSQL enforce the GORM foreign keys (shares and subscriptions reference `calendars`; contacts and shares reference `address_books`; objects, both change logs and photos have no foreign key, so nothing but this list stops them from being orphaned). Every delete is `Unscoped` (already soft-deleted objects go too), and the collection row is **hard**-deleted: nothing reads a soft-deleted collection, and ids are never reused (SQLite `AUTOINCREMENT`, PostgreSQL sequences). `lockCollections` first marks the row deleted (an `UPDATE`) to take its row lock before the contents are read; the MCP tool tests inject a storage failure with a `BEFORE UPDATE` trigger and depend on it. Every delete path ends here — `CalendarRepository.Delete`, `AddressBookRepository.Delete`, `PurgeAccountData` and the data migration `purgeDeletedCollections` (`PurgeDeletedCollections`: soft-deleted collection rows plus every row whose collection is not live). **A table keyed on a collection (or on its objects) must be added here**, or deleted collections leak its rows. A single event or contact DELETE (REST, MCP, DAV) still only soft-deletes that object row; it goes for good with its collection. A task DELETE (#170) — the REST route and a DAV client's DELETE of a VTODO object alike — is the exception: `CalendarRepository.HardDeleteCalendarObject` removes the row for good.
  - `username_lookup.go` — `findByUsername`, shared by the user and CardDAV-credential repos: exact spelling first, then a case-insensitive match (`LOWER()` in SQL) that must be unambiguous (F02 — usernames generated before registration went lowercase-only are mixed-case and are also the `/dav/{username}/` segment, so stored names are never rewritten). The CalDAV-credential repo does not use it (see below).
  - `refresh_token_repo.go` — Refresh token storage.
  - `password_reset_repo.go` — Password reset token storage.
  - `calendar_repo.go` — Calendar persistence. `ReplaceFeedObjects` makes a subscribed calendar's contents match a feed in one transaction (story 100) — one sync token per changed resource but a single calendar-row update, and an unchanged feed touches neither, so a static `.ics` republished hourly does not wake every DAV client. `Delete` permanently removes the calendar with everything in it (`collection_purge.go`) — its subscription row too, because a calendar is deleted from several places (REST/MCP use case, CalDAV collection DELETE, subscription endpoints) and none of them should have to know what hangs off it. `ListEvents` and `SearchEvents` return events only (`component_type = 'VEVENT'`, #170): they back the REST event list, `GET /search` and the MCP event tools (incl. `find_free_slots`), none of which knows tasks; a VTODO written over CalDAV would otherwise come back as an event. `ListTasks` (#170) is the task-side query: VTODOs only, status/text/due filters on the denormalized task columns, the order `(due_at IS NULL), due_at, (priority IS NULL), priority, created_at, id` (spelled out because SQLite and PostgreSQL sort NULLs differently), one page plus the total; `ListReadableCalendarIDs` (#170) resolves the calendars a user can read for the cross-list task routes in ONE SELECT (owned, subscribed included, plus those named by a live share row, as `GetUserPermission` accepts them; soft-deleted calendars and shares skipped), returning only the slim `calendar.ReadableCalendar` (id, UUID, name, colour, component set) — no owner preload and no per-calendar COUNT, unlike the calendar list use case. `CountTasks` (#170) counts the tasks of those calendars for `GET /api/v1/tasks/summary` in ONE grouped query (conditional `SUM(CASE …)` per calendar over the task columns, the `ListTasks` open/completed predicates, `is_all_day` deciding date vs instant comparison against `calendar.TaskDayOf(asOf)`, every bound UTC); it runs through GORM's Row callbacks (`Scan`), not the Query ones. `GetEventCount` counts events only too (the `event_count` of the calendar list, `/search`, MCP and the subscription views), so a task list reports 0. `HardDeleteCalendarObject` (#170, every task DELETE: the REST route and a DAV DELETE of a VTODO) is an `Unscoped` DELETE of the object row plus `recordChange("deleted")` in one transaction — no tombstone; the change-log row's path and UID are all sync needs — and a row already gone (`RowsAffected == 0`) is `calendar.ErrNotFound` with nothing recorded; `DeleteCalendarObject` (event deletes over REST, MCP and DAV, import replace) keeps the soft delete. `UpdateSupportedComponents` is how `supported_components` changes after create (#170: the widen-only PATCH, the narrowing migration): the column plus `recordChange` in one transaction; a missing or soft-deleted calendar is `calendar.ErrNotFound` with nothing written. `UpdateMetadata` cannot write that column. Everything else still sees VTODOs: `GetCalendarObjects` (CalDAV PROPFIND/REPORT, export, backup, public feed, import duplicate check), `GetCalendarObjectByPath`, the sync log, and `GetCalendarObjectByUUID` — the event and task routes, the MCP event tools and the event/task use cases filter what it returns with `CalendarObject.IsEvent` / `IsTask`.
  - `addressbook_repository.go` — AddressBook and contact persistence (with pagination and search). `Delete` permanently removes the book with its contacts, photos, change log and shares (`collection_purge.go`).
  - `app_password_repo.go` — App password storage.
  - `caldav_credential_repo.go`, `carddav_credential_repo.go` — DAV credential storage. The username's unique index also covers revoked rows, so `Revoke` rewrites the name to `revoked:<uuid>` to free it (F24; `releaseRevokedCredentialUsernames` in `RunDataMigrations` does the same for older rows), and `Create` turns a unique violation into `user.ErrCredentialUsernameTaken` (the handlers' 409), never the raw driver error. Both `GetByUsername`s accept the name in any case, by different means: the CalDAV one lower-cases the input in Go (`strings.ToLower`) and does a single plain `username = ?` match — never `LOWER()`/`COLLATE` in SQL; it relies on every stored name being lowercase (`ValidateDAVCredentialUsername`) — and answers a miss with `gorm.ErrRecordNotFound`; the CardDAV one goes through `findByUsername` and answers a miss with `(nil, nil)`.
  - `mcp_token_repo.go` — MCP access-token storage, looked up by SHA-256 of the presented secret (#104).
  - `subscription_repo.go` — Calendar-subscription storage, incl. `FindDue` (the worker's only query, story 100).
  - `calendar_share_repo.go`, `addressbook_share_repo.go` — Sharing persistence. There is deliberately no "delete every share of a collection": the collection's `Delete` removes its shares in the same transaction.
  - `oauth_connection_repo.go` — OAuth provider link storage.
  - `system_setting_repo.go` — System settings persistence.

### [auth/](auth/)

- **Purpose**: Implements authentication-related services.
- **Key Components**:
  - `jwt.go` — JWT token generation and validation. Access tokens carry `iat_ns` (issue time in nanoseconds) next to the standard `iat`; `ValidateAccessToken` returns it as `AccessTokenClaims.IssuedAt` (falling back to the whole-second `iat` for older tokens). Validation proves only signature and expiry — the caller must still check the user's revocation marker.
  - `basic_auth.go` — HTTP Basic Auth for CalDAV/CardDAV client access (app passwords and DAV credentials).
  - `oauth.go` — OIDC/OAuth2 provider management using `go-oidc` and `golang.org/x/oauth2`.

### [webdav/](webdav/)

- **Purpose**: Implements the CalDAV (RFC 4791) and CardDAV (RFC 6352) protocol backends.
- **Key Components**:
  - `handler.go` — WebDAV request dispatcher. `authenticate` asks the optional `BasicAuthLimiter` (`WithBasicAuthLimiter`, set when rate limiting is on) before it looks up or bcrypt-checks a Basic credential, and settles the check once it knows whether the request is let in (only a 401 counts as a failure); a new early return between the two must settle too. A deferred `settle(false)` covers a panic, so a check never stays pending for good. Every error it returns goes through `serveDAVError` (`errors.go`): a go-webdav `HTTPError` from our own hand-rolled sub-handlers (sync REPORT, collection PROPFIND/PROPPATCH) is answered with its status, as emersion does internally; Fiber's default handler would make it a 500 (F17). A missing and another user's collection both answer 404. A PROPFIND one level below a principal (`/dav/{x}/{y}/`) is a 404 unless it is one of the caller's own two home sets: emersion would answer any other such path — another user's home, `/dav/{me}/{anything}/` — with an empty 207 (F11). 404, not 403, like everything below another user's home; shares live under the sharee's own home and are unaffected. Answers PROPFIND/OPTIONS on `/dav/` and the principal itself (`gowebdav.ServePrincipal`, both home sets in one response); an empty PROPFIND body there is rewritten to an explicit `allprop` first, because `ServePrincipal` would otherwise answer 400 (RFC 4918 §9.1, F06).
  - `path.go` — `canonicalDAVPath`: the one form of a request path every decision is made on (F29). `Authenticate` rewrites the request to it **before** any scope or routing check, for our code (`c.Path()`) and for emersion (the request line) alike: percent-decoded once, no empty or dot segments, lower-case `/dav` mount, and a trailing slash on every collection-depth path (root, principal, home set, collection), served like the slash form with `Content-Location` naming it (RFC 4918 §5.2; no redirect, DAV clients do not reliably follow one for PROPFIND/REPORT). Fiber's `c.Path()` is raw while emersion acts on the decoded path, so any check made on the raw path can disagree with what is served — a percent-encoded `calendars` segment once let a CardDAV-only credential read and write calendars. The fixed segments stay case-sensitive (`/Calendars/` is a 404). `/dav/{other}/` deliberately keeps answering with the caller's own principal: the name is never looked up, so it reveals nothing about that account, and a client configured with a slightly different principal URL still finds its home sets.
  - `context.go` — WebDAV request context.
  - `caldav_backend.go` — CalDAV protocol operations (calendars, events, iCalendar parsing). `ResolvePath` caps a subscribed calendar (story 100) at read-only via `calendar.EffectivePermission`, which is what makes PUT and DELETE on its objects return 403 without either handler knowing subscriptions exist. Collection-level operations that are the OWNER's prerogative — deleting the collection, PROPPATCHing its displayname — therefore compare `c.UserID` against the authenticated user instead of testing for `PermissionOwner`, or the cap would lock an owner out of their own subscription. Deleting the collection is a single `CalendarRepository.Delete` (`CardDAVBackend.DeleteAddressBook`: `AddressBookRepository.Delete`) — the cascade takes events/contacts, change log, shares, subscription and public link with it. An object DELETE branches on the object's kind (#170): a task (`CalendarObject.IsTask`, a VTODO) is hard-deleted through `HardDeleteCalendarObject`, exactly like the REST task DELETE (no tombstone, the `deleted` change-log row with the new sync token in the same transaction; a row a concurrent delete already removed is a 404 with nothing recorded), every other object (an event) keeps the soft `DeleteCalendarObject`. A PUT body that parses but is not a valid calendar object (no component, no UID, two UIDs or component types, or anything the iCalendar encoder rejects) is answered with a 409 CalDAV precondition (`valid-calendar-object-resource` / `valid-calendar-data`), never a 500; validation runs before any DB lookup. Likewise `GetCalendar` maps the collection with the *uncapped* permission: that permission only picks the URL (owner path vs. share UUID), and emersion lists a Depth 1 PROPFIND's members under the returned path, so mapping an owned subscription as a share made that PROPFIND a 404 (F21).
  - `carddav_backend.go` — CardDAV protocol operations (address books, contacts, vCard parsing). A vCard PUT without VERSION is a 409 `valid-address-data`, not a 500.
  - `propfind_collection.go` — the one description of a calendar / address-book collection (`collectionProps`): sync-token, getctag, supported-report-set, displayname, the CalDAV/CardDAV properties (description, supported component set / data, max size), current-user-principal and Apple `calendar-color` (the stored `#RRGGBB`). The hand-rolled Depth:0 PROPFIND answers from it, and `rewriteCollectionResponses` splices it over every collection emersion lists at Depth 1/infinity, so a collection looks the same at every Depth (F07) — add a collection property there, never to only one path. Also reports `DAV:current-user-privilege-set` — the interoperable way to tell a client a collection is read-only, for subscriptions and read-only shares alike — and `CS:source` for a subscription. The resourcetype deliberately stays `<C:calendar/>` rather than `<CS:subscribed/>`: a client that does not know the subscribed type would stop treating the collection as a calendar and hide its events entirely.
  - Collection creation (`CreateCalendar` / `CreateAddressBook`, reached by MKCOL and MKCALENDAR): the URL is resolved first, exactly like any other request (owned path, or a share's UUID / legacy path), and a URL that already maps to a collection is a **405** (RFC 4918 §9.3.1). Neither emersion nor the schema checks this — there is no unique `(user_id, path)` index, on purpose, because existing databases may already hold duplicates — so the check is the only guard.
  - `mkcol.go` — validates every property of a MKCALENDAR or extended MKCOL before anything is created (F25): displayname, calendar-description, calendar-color, calendar-timezone / calendar-timezone-id (stored as an IANA name), supported-calendar-component-set (a non-empty subset of VEVENT/VTODO, stored and reported) and an address book's addressbook-description are applied; Apple's calendar-order and an opaque schedule-calendar-transp are accepted without being stored. Any other property refuses the whole request and creates nothing: MKCALENDAR answers 207 (RFC 4791 §5.3.1.1), extended MKCOL 403 with a DAV:mkcol-response (RFC 5689). emersion itself keeps only the displayname, so a new collection property must be handled here or it is refused.
  - `sync.go`, `sync_elements.go`, `sync_addressbook.go` — WebDAV-Sync (RFC 6578) for efficient incremental sync.
  - `proppatch.go` — the hand-rolled collection PROPPATCH (emersion's is a 501): `DAV:displayname` for both collection types, Apple `calendar-color` for calendars. All-or-nothing per RFC 4918 §9.2: any other property or any `remove` is 403, an invalid value (empty/over-long name, non-hex colour) 409, and then every other property is 424 Failed Dependency and nothing is written. A successful one goes through `UpdateMetadata`, so the rename and its sync-token bump commit together.
  - `caldav_component.go` — `checkSupportedComponents`: a PUT holding a component the collection does not store is a **403** with `CALDAV:supported-calendar-component` (RFC 4791 §5.3.2.1), wrapped as `webdav.NewHTTPError(403, caldav.NewPreconditionError(…))` because the library's precondition helper is always 409 (F27). VTIMEZONE is always fine. The allowed list is `calendarComponentSet` (in `mkcol.go`), which delegates to `calendar.SupportsComponent` (#170) and is also what `mapCalendar` advertises as `supported-calendar-component-set`: `VEVENT` and/or `VTODO`, exactly what the collection stores (legacy `""` = both). So a VTODO into an event calendar, a VEVENT into a task list and a VJOURNAL anywhere are all this 403. `PutCalendarObject` runs it before `caldav.ValidateCalendarObject`, so a VEVENT+VTODO body PUT into a single-component collection is the 403, not the 409 a mixed collection gives it.
  - `caldav_vtodo_filter.go` — `filterCalendarQuery`, what `QueryCalendarObjects` filters a calendar-query with (#170). A `VTODO` comp-filter carrying a `time-range` (a client asking for a due-date window; Thunderbird 156 never sends one, it filters its own cache) is decided here, because go-webdav v0.7.0 never matches a non-recurring VTODO and expands a recurring one with `RecurrenceSet` from DTSTART — year 1 for a DUE-only Tasks.org task. A non-recurring VTODO and each `RECURRENCE-ID` override follow the RFC 4791 §9.9 VTODO table; a recurring master (RRULE or RDATE) matches when [DTSTART else DUE, the denormalised `RecurrenceEndTime` + DTSTART..DUE] meets the window (nil = unbounded; never expanded, over-includes a little, which is safe). Everything else in the query — VEVENT time-ranges, prop-filters, text-match, the VTODO filter's own prop-/comp-filters on the same component — still goes through `caldav.Match`, and a query without a VTODO time-range goes to `caldav.Filter` unchanged. DATE and floating values are UTC (R3); a time-range without `start` is open (go-webdav ignores it, still so for VEVENT). Known go-webdav limit left alone: a prop-filter `is-not-defined` matches when the property exists.

## Design Philosophy

Adapters are where the specific technical choices (like using JSON for API or GORM for DB) are confined. By isolating these choices here, the core business logic remains portable and easy to test. This layer depends on `domain` and `usecase`.
